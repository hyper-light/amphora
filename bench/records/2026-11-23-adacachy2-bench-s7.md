# Lane S8: the checked suite run, Amphora, SQLite, Turso and PostgreSQL 19 on adacachy2 (2026-11-23)

Verdict, losses first. On this one run Amphora is behind the best competitor in 37 of the 51
statement-and-client cells by throughput. The worst are the suite's analytics: table_count trails
Turso at every client count (0.06x at 1 client, near 0x at 32 and 128), and filter_no_index,
aggregates_range, join_three and table_group_by trail PostgreSQL 19 by 6-11x in six cells at 32 and 128 clients.
Point reads trail by 1.3-4x (point_text and point_secondary at 128 clients: 0.25x of PostgreSQL).
OLTP writes are closest: insert_batch_100 trails PostgreSQL 3x at 32 and 128 clients; the rest are
within 0.64-1x or ahead. The full list is under "Losses, worst first" below.

Answers. Amphora's 1,026 read answers equal SQLite's value for value (0 differ), and so do Turso's.
PostgreSQL's differ in 373 of 1,026: point_pk (128 of 128), join_three (128), aggregates_range (116)
and table_group_by (1). Each one is listed below with its repro. Whether each is a real dialect
difference (PostgreSQL's types and formatting) or a comparison the checker doesn't yet allow for is
not yet looked at; it is listed, not judged.

How far to trust the speed numbers. Inconclusive as a ranking, useful as a map of where to look.
- One run per target, a 1 s timed window after 0.5 s warm-up per statement and client count
  (S7's script, kept as is). No repeat, so no run-to-run range.
- adacachy2 was shared: the 1-minute load average on its 32 cores was 21 at the start and 67 at
  the end of the suite (CPU pressure some avg10 44.9% at the end); each target's load before/after is
  beside every number. Later targets (SQLite, PostgreSQL) ran under more load than Amphora.
- No limiter was profiled in this run (RULES.md 0): the numbers say where Amphora loses, not why.

## The run

- Commit 701486af on perf/bench-s7 (S7's 795faa83 plus this lane's run.sh and postgres.sh fixes;
  W1's uncopied fix b83da2fe is in every Amphora row). Release build, adacachy2 (runner
  00aad8daff2fa3c9daa65d53c425d450), kiln run r1604 with needs linux/amd64,cpus=16,mem=24g.
- `bench/suite.sh amphora,turso,sqlite,postgres --only <17 statements> --items 200000 --clients 1,32,128 --seconds 1 --warmup 0.5`,
  then `python3 bench/suite_answers.py suite.jsonl` (each read's rows at each 128-client run's
  first parameters, taken untimed before any write, held to SQLite's).
- Amphora, SQLite and Turso run in the driver's process; PostgreSQL 19 (image postgres:19) as a
  local server over 127.0.0.1, fsync and synchronous_commit on, as it ships.
- S7's run r1577 (795faa83) lost every target: Amphora, Turso and SQLite failed with "./run.sh:
  line 102: /usr/bin/env: Argument list too long" (the report with its answers passed as one argument,
  past Linux's 128 KiB limit), and PostgreSQL 19 refused its mount at /var/lib/postgresql/data. Both
  are fixed in 701486af; r1577 was stopped and this run replaced it.
- Checks at 795faa83 (r1577): suite_db's unit tests pass (2 of 2); clippy's findings in suite.rs (10)
  and suite_db.rs (8) are all on lines main already had (git blame: 2603cddf, 41bba4e4, a3de3b28,
  da973dd5, fbe3f58c), none in store.rs; 701486af changes only shell.

Each cell: p50 / p99 latency in ms, throughput in statements a second, and in brackets the 1-minute load average on adacachy2's 32 cores before/after that target's whole pass (run.sh's load_before/load_after; the suite records no per-statement load).
