# Independent review of the T1 performance merges

This review covers the requested T1 and performance merges through `eb0e28dd`, the subsequent C3 durability fix, and the benchmark records on `origin/main` at `62687f5d`. Correctness runs used the verifier's builds on adacachy2 Linux and arm64 macOS. All timed comparisons used a shared host. The raw observations support individual figures below. The program's overall 10× claim remains unverified under the required release conditions of load below two and no competing builds. ## Page benchmark checks

The page suite's original `ab-0051.jsonl` and `ab2-0110.jsonl` are still on adacachy2. Each comparison contains 60 measured cells. Every cell reports zero errors, zero retries and exactly one row per operation. The raw eight-client primary-key medians reproduce the two published tables. The default path measured 1,048,047.0 to 1,004,390.8 reads/s. Plain measured 1,424,040.6 to 1,794,026.6 reads/s. [Raw-record audit](2026-11-23-adacachy2-perf-pagepath.md)

The subsequent checkout record in `6bcb4838` compares two reader-pool implementations on one binary. The six rows in `b3-checkout-0307.jsonl` report zero errors. Median point reads at 32 clients rose from 956,953/s to 1,660,041/s at loads of 76–95. The retained `ab5-0229.jsonl` has three fixed-order pairs named `hdr-after` and `after2`. The lane's separate five-round comparison isolating the WAL patch had to restart after its base build lacked a lockfile (`612f541c`).

## Recovery, visibility and wake delivery

The review fence in `67d1bab5` samples the published timestamp at reader finish. A previous snapshot is still valid for reading. Every earlier published writer must be recoverable after the successful finish. In the two-lane test both writers use buffered commits, both are absent from the reader's snapshot, and exactly two writer records reach the log.

On the pre-C3 main (`e4fd7876`), Linux r61 recorded zero flushed records and an empty recovered key set after the reader returned success. On the landed fence in `ac58af91`, Linux r53 recovered both writers. Its only failing case was the 505-root header. All 56 selected engine tests passed with the review fixes in r75, including the WAL and shared-page controls. [Two-lane power-cut test](../../crates/engine/storage/versioned/durable.rs#L1236)

Removing the new flush between page writes and the marked header made the crash sweep lose committed data at checkpoint operation 17 of 20, seed 3, first reopen. Restoring the landed SSI shortcut also made a reader return success after its budget ran out and discarded its validation evidence. Commit `01261a4a` returns the reader to SSI validation, which reports a serialization failure.

An older writer also acknowledged tree ID 505, the 506th root slot, and flushed its oversized checkpoint journal before returning `TooBig`. The next open returned `TooBig` for a database holding a durably committed row. Commit `60c8a349` refuses new growth at the existing page-format boundary and replays previously published oversized journals. A refused checkpoint on such a recovered store performs zero disk operations. The old row and a subsequent durable write both survive a power cut. An already oversized catalog requires migration before it can checkpoint again.

The versioned point-read example now verifies the key's expected value on every request and starts the clock before releasing its workers (`aac6cd6b`). The admission example reports raw completions, pressure refusals and unexpected errors (`4986b209`). The cold-open example isolates the new files for each invocation and rejects zero samples (`5cd21731`). Its earlier example could modify an existing database during the phase labelled new.

The archived release binary for the C3 reopen benchmark accepted 32 rows for a 16-row request and zero samples in Linux r30. Commit `dcf81057` checks the requested keys and values after each timed open and preserves the 100-byte workload. On arm64 the corrected example recovered 32 and then 16 rows on the same parent path, twice each, and refused zero reopens.

On `2c048c98`, a v8 loopback owner received 17 where the wire required 17,000 ns. Commit `2cdfaac3` converts at the negotiated version boundary. With 1,004 records already queued, a learned bound that shrank to two made the benchmark drain only two records. Commit `34427d33` drains the outstanding records under the queue lock. Linux r54 passed both rolling-upgrade directions and the shrinking-bound case.

Skipping probes and builds needed `94ffca24` and `42b41e67`. The write itself needed `eea8e3b8`, and an open writer abandoned by its connection needed `da50819b`. Commit `b3bccebf` fixes a separate interleaving that installed an empty cracker after the writer had already supplied row 3.

A completed background build also left its versioned snapshot open. After the build's worker exited and a new row committed, the oldest open snapshot stayed at 3 while the latest commit reached 4. Closing the private versioned read in `0dbbcf85` let the collection watermark reach 4.

The cross-group wake fix is `9345d7db`. A retry after a lost resolution reply finds a completed operation, so it cannot reconstruct the first release's list of keys. In Linux r68 the retry answered Resolved on `e4fd7876`, while the waiting read returned Timeout after 120.16 s. The original durable callback must ring the waiting reads. Linux r54 and r65 verified row `[7]` and exactly one keyed wake. W10, W11 and W13 passed, including the follower's own apply. W11 executed the session twice in Wait and three times in WaitOnLock.

The as-of read also missed a held binary key ending in `ff61`. Commit `3e5892ef` uses the next family prefix as the exclusive end of the lock scan. A separate follower trace acknowledged write index 7 while its closed index was still 6. Commit `6110f8b4` waits for the internal write's application before returning its timestamp to the cross-group coordinator.

For busy SQL statements, `0d33fb4d` gives each statement its own removable wake subscription. Commit `917765f6` waits for writer unlock when a read-to-write upgrade fails. Previously, releasing the upgrader's own read mark triggered immediate retries while the writer still held the lock. The join checks also found a merge-join plan emitted as a parallel hash aggregate (`eb7fbc1d`) and a prepare-time panic when only an aggregate FILTER referenced a column (`98af4fe0`).

## Follow-up durability checks

After a process dies, its replacement can read complete writes that the OS still holds in cache. The next power cut can lose those writes. Two Linux regressions exercise that sequence.

- At seed 3 the original redo writer stopped between its write and its flush. A replacement read its row, completed the read-only transaction, and durably committed another row on a second lane. Linux r78 recovered neither row after power loss. Commit `09f3c209` syncs nonempty retained redo files and any truncations before recovery reports the prefix durable. In r79 all 25 durability and six redo tests passed.
- At checkpoint operation 7 of 21, seed 3, the replacement process adopted a complete journal from cache and wrote its header. All acknowledged rows were readable. After power loss, the second reopen reported a corrupt database because the named journal was gone. Commit `477da701` syncs the selected journal before recovery can rely on it, including when an older recovery has already written a matching header. This adds one journal sync per reopen. Linux r85 passed both crash sweeps, all 26 durability and six redo tests, and all-target engine Clippy.

Both fixes are on `origin/t1/main-review`. The earlier C3 read-only commit fix `67d1bab5` from the same branch is present on main as `b6cb6aa8`. The stable patch IDs match.

## Coordinator decisions, November 24 UTC

- **Descriptor exhaustion** — The queued contract tries the syscall on every acquire and returns a typed refusal immediately on EMFILE or ENFILE. The budget counts descriptors for reporting. On exhaustion the listener uses its reserve descriptor to accept, refuse and close the pending connection, replenishes the reserve, and resumes waiting on the listening socket. The listener is the only production caller of the old release wait on the checked main.
- **Cross-group recovery** — Before taking the first lock, every participant must have negotiated the version needed to finish the transaction, currently v9 for ResolveAt and RecoverAt. Amphora is unreleased and the current contract excludes recovery of transactions started on v8 under v9. Timestamp recovery across versions is a design item before any release supporting mixed-version fleets.
- **Calibration on a shared home directory** — The queued key includes a hash of Linux's machine ID, macOS's IOPlatformUUID, or Windows's MachineGuid alongside the CPU record and executable path, length and mtime. Failure to read the identity triggers a fresh measurement.
- **Engine production gate** — The cleanup lane will fix violations in code, starting at the T1 merge's sites, and lower the ceilings where the diagnostic counts fell. Its landing will be checked at its exact SHA.
